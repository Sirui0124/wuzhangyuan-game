## 初审发现（实施前记录）

1. 已统一选择展示，但未统一章节运行协议。entry.ts分别动态载入game.ts、chapter-two.ts、chapter-three.ts、chapter-four-rescue.ts、chapter-five.ts和chapter-seven.ts。不同入口分别管理请求、渲染、存档、暂停和恢复。session/contracts.ts目前只定义身份，不是统一运行协议。应先抽取共同生命周期，再决定是否统一内容格式。
2. 第一章旧推理不是完全闲置代码。narrative-decision.ts仍使用inferenceRules，session.ts仍维护graph、edges、positions、thinking。要用直接剧情条件替换原推理，先将每个条件映射到真实调查、人物应允和行动完成事件；不能整目录删除。
3. 存档策略不同。第二章显式重建状态并校验已读判断；第三章保存检查点；第五章重放动作。建议统一外层身份、版本、备份和恢复结果，但保留各章必要的事实验证，不强迫一次性转换全部存档。
4. 第四章通过iframe接入demos/yiling-rescue，是独立玩法和运行系统。是否保留多路营救，影响能否把全游戏收敛为剧情与选择，必须由用户决定。不要把另一个UI原型目录误认作当前运行入口。
5. 人格评估虽然不拥有剧情事实，仍接入确认发言、死亡、重试、存档和暂停菜单，并拥有额外模型任务与数据记录。是否保留是重要功能取舍。
6. 语音和剧情判定有并行处理；第一章声音播放完成会参与回复交接。统一请求取消时应保持语音失败可回落文字，不能让声音错误卡住剧情。
7. index.html仍加载多份旧思绪与表达样式。旧文件可能兼有现用规则，建议以页面实际样式覆盖验证后逐块合并，不按文件名整批删除。
8. 游戏运行、开发片场、美术预览、Cocos工程和安装器并存。开发工具应与发布包分离；保留工具不代表必须随游戏加载，Cocos是否继续是独立产品决定。

## 建议目标结构（提案）

游戏外壳：入口、导航、设置、暂停、存档、媒体。
章节内容：对白、选项、线索、条件和结果。
章节运行接口：读取当前展示、确认动作、导出/恢复进度、结束与销毁；特殊玩法作为章内适配器。
可选服务：NPC语义理解、润色、语音；失败/取消不授予事实。
统一展示：剧情、选择、表达、线索和结果；展示只发出动作，不直接改剧情标记。

依赖方向：展示提交动作 → 运行器校验条件 → 写入事实/选择 → 生成新展示。AI返回结构化建议或判断，由运行器校验并应用。不要引入通用插件注册器、动态事件总线等尚无明确需求的层。
